# Heartbeat 检查清单

每次心跳逐条判断，只有命中才提醒。通用纪律：

- 输入里带最近已发通知——**同一件事同一天不重复提醒**，别变成唠叨
- 多条命中合并成一条提醒，按紧急度排序

1. **会议**：日历中 20 分钟内即将开始的日程 → 提醒（含会议名和开始时间）
2. **GitHub**：有等我 review 的 PR、或我的 PR 已被 approve 可以合了 → 提醒
3. **邮件**：未读中有真人发来的、等待回复超过半天的 → 提醒
4. **催办**：行动队列里挂了超过 3 小时的待处理项 → 汇总催一次（「还有 N 件事等你：xxx、xxx」）。
   同一批事已经催过（见最近已发通知）就闭嘴；snoozed 的不算
5. **承诺**：记忆里「进行中的承诺」有今天/明天到期或已逾期的 → 提醒（含对谁承诺和 due）。
   已经提醒过的当天不重复
6. **职责**：routine 草稿（站会/周会/周报）已生成但临近截止仍未人审 → 提醒去今日页过一眼再派写入
7. **收尾**：22:00 之后仍有未验收的引擎任务、未处理的行动项或待审草稿 → 提一句收个尾。
   （工作日志由自动收割负责，不需要提醒手动 wrap）

## 观察（放进助理货架，输出 `observations`，不推送）

提醒之外，留意这三类，命中才写，每次最多 2 条：

- **suggestion**：能让 owner 少操心的具体一步（例：某 PR 挂了 3 天没人 review → 建议开一条跟进）
- **risk**：还没出事但正在变坏的苗头（例：同一仓库 CI 连续失败、承诺 due 临近却没有相关进展）
- **pattern**：反复出现的规律（例：每天同一时段被同一类消息打断）

纪律：

- 上下文里「货架上已有的观察」列出的，**不要换个说法再给一遍**
- 「待处理的行动」里已经挂着的事**不写成观察**：催它、建议集中/合并处理它，都归第 4 条催办，写进 `message`。
  观察确实牵涉某条行动时，`actionPayload.relatesTo` 填那条的 `id`
- title / detail / actionPayload 里不写条数和「挂了多久」——数字明天就过期，写事情本身
- 只依据上下文包里出现过的事实，`detail` 写清依据；拿不准就不写
- 建议派编码任务（kind=task）时，`prompt` 要能直接交给 agent 执行；`dir` 只在上下文出现过明确路径时填，否则省略
- 已经写进 `message` 的事不要再当观察
